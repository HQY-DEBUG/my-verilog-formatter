# 版本更新规则

## 更新时机

- 每次完成一次仓库更新，必须在交付和提交前更新插件版本；代码、资源、测试、配置、文档和仓库规则的修改均适用。
- 只读分析、答疑和没有文件变更的任务不更新版本。
- 同一次任务中的编辑、修正和验证共用一个新版本，不因重复执行命令而连续升版。
- 用户明确指定版本或要求本次不升版时，以用户指令为准。

## 版本选择

- 以 `package.json` 的 `version` 为唯一版本基准；未指定版本时，默认将补丁版本加一，例如 `1.4.2` 更新为 `1.4.3`。
- 用户指定次版本或主版本更新时，按指定版本执行，并将更低位版本归零。
- 新版本必须高于本次更新开始时的版本；发布时不得复用 Marketplace 已发布的同一平台版本。
- 保持 `name` 为 `hanxuyao-plugin`、`publisher` 为 `hanxuyao`，除非用户明确要求修改插件身份。

## 同步范围

1. 更新 `package.json` 的 `version`。
2. 同步 `package-lock.json` 的顶层 `version` 和 `packages[""].version`，不得因此修改依赖版本。
3. 同步 `README.md` 顶部版本、日期和安装示例中的版本号；在修改记录表最前面增加当前版本说明。日期使用 `YYYY/MM/DD`，保留已有历史记录。
4. 本次实际修改的源码文件若已有版本、日期和修改记录头，按原有格式同步当前版本和变更说明；不批量改写未修改文件的历史头。
5. 需要生成安装包时，文件名及 VSIX 内部版本必须与 `package.json` 一致。当前发布目标为 `win32-x64`。

## 完成检查

- 确认版本清单、README 当前版本和本次修改记录一致，历史记录中的旧版本保持原样。
- 完成根目录 `AGENTS.md` 中适用的验证，将版本变更与本次更新一并提交。
- 版本递增不代表已发布；仅在用户要求打包或发布时执行相应操作，并如实报告结果。
